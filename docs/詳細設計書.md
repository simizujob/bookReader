#### 4.1a `judge(isbn:)`がオフラインで返せる範囲について（重要な設計判断）

要件定義書F-02は「シリーズの一部を所持しており、当該巻は未所持」という判定もオフライン即時表示の対象としている。しかし、**スキャンした本（まだ所持していない本）のシリーズ名・巻数はローカルDBのどこにも存在しない**（ローカルDBは自分が登録した所持本の情報しか持たない）。この情報を得るにはOpen Libraryへの問い合わせが必要であり、オフラインでは原理的に取得できない。

そのため本設計では以下のように役割を分離する。

- `BookRepository.judge(isbn:)`はオフラインで確実に判定できる`.owned` / `.notOwned(possibleEdition:)`の2値のみを同期的に返す（要件定義書N-01/N-02の「即時・オフライン」を満たす核）。
- 「シリーズの一部を所持、当該巻は未所持」という**文脈付きの表示**は、非同期のOpen Libraryメタデータ取得（4.7）が成功し、取得した本のseriesKeyがローカルで部分所持中のシリーズと一致した場合に、`PreCheckViewModel`側で表示を書き換える形で実現する（5.1参照）。
- オフライン時は`.notOwned`のプレーンな表示に留まり、「同シリーズの一部を所持」という文脈は付与されない。これは意図した制約であり、要件定義書F-02の受け入れ基準（版・巻の区別表示）自体はオンライン時に満たされる。

```swift
// BookRepositoryImpl.judge の実装方針（同期・オフライン専用）
func judge(isbn: String) throws -> JudgeResult {
    if let existing = try find(isbn: isbn), existing.status == .owned {
        return .owned
    }
    return .notOwned(possibleEdition: nil)  // このISBN単独ではタイトルが未知のため、版違い判定はまだ行わない
}
```

同じ理由で、`fuzzyMatch(title:)`による版違い警告も「タイトルが分かって初めて判定できる」処理であり、**ISBNバーコードのみのスキャン直後には実行できない**（バーコードにはタイトルが含まれない）。したがって`fuzzyMatch`の呼び出しは`judge()`の同期フローから外し、5.1で述べる非同期メタデータ取得の後段に移す。**基本設計書6.1のシーケンス図は、`fuzzyMatch`をjudge直後の同期処理として描いていた点が誤りであり、本書の修正に合わせて基本設計書側も併せて修正する**（後述の修正一覧を参照）。

**`insert`/`insertBatch`/`update`/`delete`の内部処理順序**（基本設計書5.6・5.7を反映）:

```
insert / insertBatch / update の場合:
1. CoreDataへの書き込み（NSManagedObjectContext.save()）
2. seriesKey = SeriesKeyNormalizer.normalize(seriesName) を計算して保存（seriesNameがnilならseriesKeyもnil）
3. afterWrite(new: 更新後のBook, previous: 更新前のBook?) を呼ぶ
     → NotificationServiceへの通知スケジュール/キャンセルを判定・実行（5.6の遷移ルール表に従う）
     → WidgetCenter.shared.reloadTimelines(ofKind: "TsundokuSummaryWidget") を呼び出す
4. 呼び出し元（ViewModel）へ更新後のBookを返す

delete の場合:
1. CoreDataからの削除前に対象Bookを取得
2. CoreDataから削除（NSManagedObjectContext.save()）
3. afterDelete(_ deleted: Book) を呼ぶ
     → NotificationService.cancelReminder(bookID:) を呼ぶ
     → WidgetCenter.shared.reloadTimelines(ofKind:) を呼び出す
```

`afterWrite(new:previous:)`と`afterDelete(_:)`は`BookRepository`実装内のprivateメソッドとして共通化し、各書き込み/削除メソッドから必ず経由させることで、通知/Widget更新の呼び忘れを構造的に防ぐ（基本設計書で指摘した「一元化」の具体化）。

### 4.3 SeriesKeyNormalizer

```swift
enum SeriesKeyNormalizer {
    static func normalize(_ raw: String) -> String {
        var s = raw
        // 1. 全角英数記号→半角（NFKC正規化に相当）
        s = s.applyingTransform(.fullwidthToHalfwidth, reverse: false) ?? s
        // 2. 前後および連続空白の除去
        s = s.trimmingCharacters(in: .whitespacesAndNewlines)
        s = s.replacingOccurrences(of: #"\s+"#, with: "", options: .regularExpression)
        // 3. 末尾の巻数表記を除去（例: "(1)" "1" "第1巻" "vol.1"）
        s = s.replacingOccurrences(
            of: #"(\(\d+\)|第?\d+巻?|[vV]ol\.?\s?\d+)$"#,
            with: "",
            options: .regularExpression
        )
        // 4. 小文字化
        return s.lowercased()
    }
}
```

### 4.3a TitleParser（シリーズ名・巻数の抽出）

**背景**: Open Library APIは書籍のタイトル文字列（例: `"鬼滅の刃 19"`）を返すのみで、「シリーズ名」「巻数」を構造化フィールドとして提供しない（要件定義書14章のリスクの通り、そもそも網羅性自体も低い）。同様に、背表紙OCR（F-03）が抽出するのも単なる文字列であり、シリーズ名と巻数が分かれているわけではない。

そのため、**タイトル文字列からシリーズ名・巻数を分解する処理を`TitleParser`として一箇所に切り出し、F-01（OCR登録時）・F-03・Open Libraryバックフィル（4.8）のすべてがこれを経由する**ことで、`Book.seriesName` / `Book.volumeNumber`を一貫した方法で導出する。

```swift
enum TitleParser {
    /// 生のタイトル文字列を (表示用title, seriesName, volumeNumber) に分解する。
    /// 末尾に巻数パターンが見つからない場合は seriesName = nil, volumeNumber = nil とし、
    /// 単巻本（シリーズに属さない本）として扱う。
    static func parse(_ rawTitle: String) -> (title: String, seriesName: String?, volumeNumber: Int?) {
        let pattern = #"(.+?)[\s　]*(?:\((\d+)\)|第(\d+)巻|[vV]ol\.?\s?(\d+)|[\s　](\d+))$"#
        guard let match = rawTitle.firstMatch(of: try! Regex(pattern)) else {
            return (rawTitle, nil, nil)
        }
        let seriesName = String(match.1)
        let volumeNumber = [match.2, match.3, match.4, match.5].compactMap { $0 }.first.flatMap { Int($0) }
        return (rawTitle, seriesName, volumeNumber)
    }
}
```

上記の`Regex`/キャプチャ取得部分は正規表現の意図を示す疑似コードであり、実装時は`NSRegularExpression`または型付き正規表現リテラル（`/pattern/`）など、Swiftのバージョンに応じた確実な方式に置き換える。

`seriesName`が得られた後は`SeriesKeyNormalizer.normalize(seriesName)`を通して`seriesKey`を導出する（4.3参照）。`TitleParser`は「分割」、`SeriesKeyNormalizer`は「分割済みのシリーズ名を正規化してキー化する」という役割分担であり、両者は必ずセットで使用する。

**適用箇所**:
- F-01（本棚一括登録）: バーコードで検出しOpen Libraryからタイトルを即時取得できた場合、および背表紙OCR（F-03）でタイトルを抽出した場合のいずれも、`BookDraft`を組み立てる前に`TitleParser.parse`を通す。
- 4.8 メタデータバックフィル: `applyMetadata`内で同様に`TitleParser.parse`を適用し、`seriesName`/`volumeNumber`/`seriesKey`も合わせて更新する（後述）。

**アルゴリズム（基本設計書5.2の具体化）**:

```
recognizeTitle(image):
    candidates = []
    for angle in [0, 90, -90]:
        rotated = image.rotated(by: angle)
        request = VNRecognizeTextRequest()
        request.recognitionLanguages = ["ja-JP", "en-US"]
        request.recognitionLevel = .accurate
        request.usesLanguageCorrection = true
        results = try VNImageRequestHandler(cgImage: rotated).perform([request])
        best = results.observations.max(by: confidence)
        if best != nil:
            candidates.append(OCRResult(text: best.text, confidence: best.confidence, rotationUsed: angle))
    return candidates.max(by: confidence) ?? OCRResult(text: "", confidence: 0, rotationUsed: 0)
```

3方向とも実行するため、1回あたりのOCR処理コストは単方向の約3倍になる。**Day3-4の実装時に実機で処理時間を計測し、体感で遅い場合は「まず0度のみ実行し、信頼度が閾値未満のときだけ90度/-90度を追加実行する」段階的方式に切り替える**（9章 未確定事項に記載）。

- 信頼度閾値: `0.5`未満は確認UI（`ConfirmCandidateSheet`）へ。
- あいまい一致の閾値: `0.8`以上を高確信度一致（後述4.7）。

backfillPendingMetadata():

呼び出し側（`WishShelfViewModel.openStoreSearch(for:)`）は以下の優先順位でURLを選択する。

```
1. series.nextVolumeISBN が存在する（F-02で当該巻を明示的にスキャン済み）→ amazonSearchURL(isbn: nextVolumeISBN)
2. 存在しない（純粋な自動提案）→ amazonSearchURL(keywords: "\(series.seriesName) \(series.nextVolumeToBuy ?? 1)巻")
```

将来のストア追加に備え`enum Storefront { case amazon }`でラップしておく。

## 6. エラー設計

| Service | エラー型 | 主なケース |
|---|---|---|
| BarcodeScanService | 例外throwなし（`nil`で未検出を表現） | Visionリクエスト自体の失敗は`error(String)`にラップしログのみ |

| `OpenLibraryError`全般 | 画面上は表示しない（サイレントフォールバック、基本設計書8章の方針を踏襲） |
| カメラ権限拒否 | 画面内バナー＋「設定を開く」ボタン（`UIApplication.openSettingsURLString`） |

## 8. テスト設計

### 8.1 単体テスト対象

| 対象 | 主なテストケース |
|---|---|
| `TitleParser.parse` | 「鬼滅の刃 19」「鬼滅の刃(19)」「鬼滅の刃 第19巻」等からseriesName="鬼滅の刃"・volumeNumber=19を抽出できること。巻数パターンがない単巻タイトルはseriesName/volumeNumberともnilになること |
| `SeriesKeyNormalizer` | 全角/半角混在、末尾巻数表記あり/なし、空白混入パターンが同一キーに正規化されること |
| `TitleMatcher.similarity` | 完全一致=1.0、全くの別タイトル≒0、表記ゆれ（括弧・記号差）で閾値0.8以上になること |
| `BookRepository.isDuplicate` | 同一ISBN→true、別ISBN+高類似タイトル→true、無関係な本→false |
| `BookRepository.judge` | 所持/未所持の2パターンが機内モードでも正しく返ること（「シリーズの一部を所持」表示は`PreCheckViewModel.enrichAfterMetadata`側のロジックであり、ここでは対象外。4.1a参照） |
| `PreCheckViewModel.enrichAfterMetadata` | メタデータ取得成功時にeditionWarning/partialSeriesInfoが正しく設定されること、取得失敗/オフライン時はenrichedContextが初期値のまま変化しないこと |
| `SeriesProgressCalculator` | 既刊総数あり/なしそれぞれでの`completionRate`・`missingVolumes`・`nextVolumeToBuy`算出 |
| `NotificationService`遷移ルール | 5.6章の遷移ルール表の全パターン（スケジュール/キャンセルの発火有無） |
| `AffiliateLinkService.amazonSearchURL`（ISBN版/キーワード版とも） | いずれも`tag=taros0480x84e-22`が常に付与されること |
| `WishShelfViewModel.openStoreSearch` | `nextVolumeISBN`の有無でISBN検索/キーワード検索が正しく切り替わること |

### 8.2 UIテスト対象（主要フロー）

1. 本棚に登録（複数冊）→積読リストに反映される
2. 買う前チェックで登録済みISBNをスキャン→「所持している」が表示される（機内モードでも成立）
3. 積読リストでチェック→読了セグメントに移動する
4. 気になる本棚でシリーズカードをタップ→SFSafariViewControllerが開く
5. 本の詳細で編集・削除→一覧に反映される

## 9. 未確定事項・実装時に決定する項目

- OCRの3方向回転を毎回全実行するか、0度優先で必要時のみ追加実行する段階的方式にするかは、Day3-4の実機計測結果で決定する（4.5参照）。
- `PreCheckViewModel.failureThresholdForManualSearch`（手動検索導線を出す連続失敗回数、暫定5回）は実機テストで調整する。
- `OpenLibraryService.fetchSeriesVolumeCount`の推定ロジック（検索結果件数を既刊総数とみなす暫定方式）は精度検証の上、明らかに不正確な場合は既刊総数取得自体を諦めフォールバック固定にする判断もあり得る。
- Widget用の`TsundokuSummaryEntry`が「最長経過日数の本」をどう選定するか（`elapsedDays`降順の先頭1件、が現状の想定）の最終仕様。
- `TitleParser`の正規表現パターンが実際のOpen Library／OCR抽出タイトルの表記とどの程度一致するかは実データでの検証が必要（「第19巻」「19巻」「(19)」以外の表記、英数字併記タイトル等は精度が落ちる可能性がある）。抽出に失敗した本は単巻本として扱われるため、致命的な誤動作にはならないが、F-05のシリーズ集計精度に影響する。
