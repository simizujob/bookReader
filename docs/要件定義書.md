## 1. 文書の目的

本書は、企画提案書「積読レーダー」の内容を実装可能な粒度に落とし込み、機能要件・非機能要件・データ要件・外部インターフェース要件・受け入れ基準を定義するものである。開発着手前のスコープ合意、および実装後の受け入れ判定の基準として用いる。

---

## 2. プロジェクト概要

### 2.1 背景・課題

蔵書数が多い読書家、特にコミック全巻・文庫シリーズを収集している層は、「この巻をもう持っているか」を正確に覚えていられず、書店・古本屋で二重購入してしまうことがある。ブクログ・読書メーターなど既存の読書記録アプリは感想共有・SNS投稿が主目的であり、外出先での即時照合（買う前チェック）に最適化されていない。

### 2.2 プロダクトコンセプト

書店で背表紙・バーコードにかざした瞬間に「持っている／持っていない／その巻は未所持」を判定する。ネットワーク接続なしで完結する即時性を核とし、加えて積読管理・シリーズ完結率管理・次の一冊への購入導線を統合することで、判定だけで終わらない継続利用理由を作る。

### 2.3 ターゲットユーザー

- 蔵書数が多い読書家
- 特にコミック全巻・文庫シリーズを収集していて「何巻まで持っているか」を把握しづらいユーザー

### 2.4 解決する課題

- 書店・古本屋での二重購入の防止
- 既存アプリに欠けている「購入判断の瞬間に使える即時照合」の提供

### 2.5 独自性・差別化ポイント

- ローカルDB完結の即時判定（電波状況に左右されない、書店内で高速動作）
- シリーズ・巻数単位での所持管理（既存アプリに無い機能）

### 2.6 収益モデル概要

- 蔵書一覧・積読リスト画面へのバナー広告表示
- 判定結果画面（買う前チェック）は広告非表示とし体験を優先
- 「気になる本棚」からの書店リンクにアフィリエイトIDを付与し購入導線自体を収益化
- 将来的に広告非表示IAPを追加

### 2.7 サーバー要否

サーバー不要。判定ロジックはCoreDataのみで完結する。Open Library APIはメタデータ（タイトル・表紙画像）取得のためのオプション呼び出しに留まり、オフライン時は判定機能自体は成立したまま表示のみ簡略化される。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 買う前チェック | 書店でバーコード等をスキャンし、所持・未所持を即時判定する機能 |
| 積読リスト | `status = owned` かつ `readStatus = unread/reading` の本の一覧 |
| 気になる本棚 | 未所持と判定された本、およびシリーズ続刊候補（wishlist）をまとめた画面 |
| 完結率 | シリーズの既刊巻数に対する所持巻数の割合（`SeriesProgress.completionRate`） |
| 既刊 | シリーズが現時点で発売済みの巻数。Open Library APIから取得する（F-05参照）。同APIのデータ網羅性の制約上、取得できない・不正確な場合がある |
| ISBN | 書籍に印字される識別番号。「作品」単位ではなく「その版で出版された1冊」単位に割り当てられるため、単行本・文庫版など版が異なれば同じ内容の本でも別のISBNになる（F-02の版違い警告を参照） |
| 所持ステータス（OwnershipStatus） | `.owned`（所持）／`.wishlist`（気になるリスト） |
| 既読ステータス（ReadStatus） | `.unread`（未読）／`.reading`（読書中）／`.finished`（読了） |

## 4. スコープ

### 4.1 MVPスコープ内

1. 本棚一括登録（撮影ベース）
2. 買う前チェック（即時所持判定）
3. 積読リスト管理（経過日数表示・通知リマインド・読了記録）
4. 気になる本棚（未所持管理・シリーズ完結率・購入導線）
5. ホーム画面ウィジェット
6. 広告表示（バナー・インタースティシャル）
7. 書店検索への購入導線（アフィリエイトリンク）
8. 登録済みの本の編集・削除

### 4.2 スコープ外（将来拡張・Future Ideas）

- 家族間での蔵書共有（App Groups / iCloud共有）
- 貸し借り管理
- 古本買取価格の目安表示
- 読書ログの年間サマリー化
- リワード広告によるリスト上限解放
- 複数書店の一括比較機能（IAP）
- オンデバイスレコメンド生成
- 後押し実績（月次サマリー）の振り返り表示

上記は本要件定義書の対象外とし、別途企画・要件化を行う。

## 5. 機能要件

各機能はID、優先度（Must/Should/Could）、概要、詳細仕様、受け入れ基準で定義する。優先度は原則としてMVPロードマップ（Day1-14、第12章）に基づきMustとするが、レビューで追加提案したF-09のみShould（次点）とする。

### F-01 本棚一括登録

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 画面 | 「本棚に登録」 |
| 概要 | 自宅の本棚をカメラでかざすだけで複数冊を一括検出し、まとめて登録する |

**詳細仕様**
- カメラのビューファインダーに写る書籍を連続的に検出し、検出数をリアルタイム表示する（例：「12冊 検出中」）。
- バーコード（ISBN/EAN-13、プレフィックス978/979）が検出できる本はバーコード優先で認識する。日本の書籍には価格情報を表す別形式のバーコード（Cコード+価格のJANバーコード）が併記されることがあるため、978/979で始まらないバーコードはISBNとして扱わない。
- バーコードが写らない背表紙は、背表紙タイトルのOCR（文字認識）で自動補完する。
- 検出結果をサムネイル一覧で表示し、「この◯冊を登録する」ボタンで一括登録を確定する。
- 既に登録済み（同一ISBNまたは高確度一致タイトル）の本は重複登録しない。

**受け入れ基準**
- 複数冊が写った本棚を撮影した際、バーコードが写っている本はISBNベースで正しく検出されること。
- バーコードが写らない背表紙でも、タイトル文字が判読可能な場合はOCRで候補が抽出されること。
- 登録確定後、CoreDataに `status = .owned` として保存されること。
- 同一ISBNの本を再度読み取っても重複レコードが作成されないこと。

### F-02 買う前チェック（即時所持判定）

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 画面 | 「買う前チェック」 |
| 概要 | 書店でバーコードにかざすと、ネットワーク接続なしで即座に所持・未所持・巻の重複を判定する |

**詳細仕様**
- カメラをかざすとVisionフレームワークのバーコード検出（EAN-13、プレフィックス978/979のISBNバーコードのみを判定対象とする）でISBNを抽出する。978/979で始まらないバーコード（価格表示用のJANバーコード等）は無視する。
- 抽出したISBNをCoreData内の登録済みデータと即時照合し、以下のいずれかを判定する。
  - 所持している（同一ISBN、または同シリーズの当該巻を所持）
  - 所持していない
  - シリーズの一部を所持しており、当該巻は未所持
- 判定はネットワーク接続なしで完結すること。
- 判定後、任意でOpen Library APIからタイトル・表紙画像を取得し表示を補完する（オフライン時は省略可、判定結果自体には影響しない）。
- 未所持と判定された場合、判定結果画面から「気になるリストへ」ワンタップで追加できる。
- ホーム画面ウィジェットからの起動導線はF-06を参照。
- ISBNが登録済みデータと完全一致しない場合でも、F-03で用いるあいまいタイトル一致ロジックを流用し、登録済みタイトルとの類似度を判定する。高い類似度で一致する場合（単行本・文庫版など版違いの可能性）は、「持っていません」と断定せず「同じタイトルの別版を登録済みかもしれません」という警告表示に切り替える。

**受け入れ基準**
- 機内モード（ネットワーク遮断）状態でも、登録済みISBNのバーコードをスキャンした際に正しく所持判定が行われること。
- シリーズものについて、既刊のうち一部のみ所持している場合、「持っています（既刊n〜m巻）」「n巻は未所持」のように、所持済み巻と未所持巻を区別して表示すること。
- 未所持判定時、「気になるリストへ」タップで即座に `status = .wishlist` として登録されること。
- 判定結果画面には広告が表示されないこと。
- 価格表示用のJANバーコード等、ISBN以外のバーコードを誤ってISBNとして認識しないこと。
- ISBNが完全一致しないが登録済みタイトルとあいまい一致する場合、「未所持」と断定せず版違いの可能性を警告表示すること。

### F-03 背表紙OCRフォールバック

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 概要 | バーコードが読み取れない背表紙に対し、タイトル文字認識で登録・照合を行う |

**詳細仕様**
- VNRecognizeTextRequestで背表紙のタイトル文字列を抽出する。認識言語は日本語（`ja-JP`）を必須設定とする。和書の背表紙は縦書き表記が大半であるため、縦書きレイアウトでも読み取れるよう画像の向き補正を行った上で認識処理にかける。
- 抽出したタイトルを既存登録データとあいまい一致（表記ゆれを許容する類似度判定）で照合する。
- 認識の確信度が低い場合のみ、ユーザーに確認UIを表示し、候補選択または手動修正を求める。
- 確信度が十分に高い場合は確認UIを表示せず自動登録・自動判定する。
- バーコード・OCRのいずれでも認識できなかった場合の手動追加導線はF-09を参照。

**受け入れ基準**
- バーコードのない背表紙（文庫本の古い版など）でもタイトルの自動抽出が試みられること。
- 縦書きの背表紙タイトルに対しても認識処理が実行されること（完全一致精度までは保証しないが、処理自体がスキップされないこと）。
- 認識確信度が閾値未満の場合、候補が確認UIとして提示され、ユーザーが確定操作をするまで登録されないこと。

### F-04 積読リスト管理

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 画面 | 「積読リスト」 |
| 概要 | 所持している未読本を経過日数つきで一覧表示し、長期積読を通知でリマインドする |

**詳細仕様**
- `status = .owned` の本を「未読／読書中／読了」のセグメントで切り替えて一覧表示する。
- 各行に `registeredAt` からの経過日数をバッジ表示する（例: 「62日」）。閾値超過時は警告色で表示する。
- 各行にチェックボタンを設け、ワンタップで既読（`readStatus = .finished`）に更新できる。
- `registeredAt` から30日経過しても `readStatus = .unread` のままの本について、UserNotificationsでリマインド通知を送信する。閾値30日は固定値とし、MVPでは設定変更UIを設けない。
- 「本棚に登録」（F-01）で一括登録した既存の蔵書についても `registeredAt`（＝アプリへの登録日）を起点に経過日数をカウントする。実際の購入時期とは一致しない場合があるが、これは意図した仕様とする。

**受け入れ基準**
- 未読本の一覧が `registeredAt` の経過日数とともに正しく表示されること。
- 登録から30日を超えた未読本について、通知が1回以上送信されること。
- 一覧画面上でチェック操作により `readStatus` が更新され、対象セグメントから除外されること。

### F-05 気になる本棚（シリーズ管理・購入導線）

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 画面 | 「気になる本棚」 |
| 概要 | 未所持本・シリーズ続刊候補を集約し、完結率を可視化した上で書店検索への購入導線を提供する |

**詳細仕様**
- シリーズごとに `SeriesProgress`（所持巻数／既刊巻数、完結率、次に買うべき巻）を算出し、カード形式で表示する。
- 完結率をプログレスバーで表示する（例: 2/3巻、66%）。
- 完結率が閾値（例: 残り1冊）を超えた場合、「🎉 あと1冊で完結」のようなポジティブな表現で強調表示する。
- 各シリーズカードに「楽天ブックスで探す」「Amazonで探す」等の書店検索ボタンを設け、ISBNから検索URLを生成しSFSafariViewControllerで開く。
- 生成する検索URLにはアフィリエイトIDを付与する。Amazon宛のリンクにはAmazonアソシエイトのトラッキングID `taros0480x84e-22` を `tag` パラメータとして付与する（例: `https://www.amazon.co.jp/s?k=<ISBN>&tag=taros0480x84e-22`）。楽天ブックス側のアフィリエイトIDは別途取得後に追記する。
- 未所持判定時（F-02）に追加された本もこの画面に集約表示される。
- 既刊総数（シリーズが何巻まで発売されているか）はOpen Library APIから取得する。同APIは日本のコミック・シリーズ情報の網羅性が低く、既刊総数が取得できない、または不正確な場合がある点を既知の制約として受け入れる（第14章リスク参照）。
- Open Library APIから既刊総数を取得できなかった場合は、完結率・`missingVolumes` を「不明」として扱い、`nextVolumeToBuy` は所持巻の最大値+1（例: 1〜17巻所持なら18巻）を暫定候補として提案するに留める。この場合、完結率プログレスバーおよび「あと1冊で完結」等の強調表示は行わない。

**受け入れ基準**
- 同一シリーズ名で複数巻を所持している場合、`ownedVolumes` / `missingVolumes` / `completionRate` が既刊情報との差分から正しく算出されること。
- 完結率が閾値を超えたシリーズには専用の強調表示が行われること。
- 既刊総数が取得できないシリーズについては、完結率を断定表示せず、所持巻の最大値+1を「次の巻候補」として表示すること。
- 書店検索ボタンタップで、該当書籍のISBNを含む検索URL（アフィリエイトID付き）がSFSafariViewControllerで開かれること。

### F-06 ホーム画面ウィジェット

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 概要 | WidgetKit（App Groups）を用い、ホーム画面から「買う前チェック」および積読リストの状況に直接アクセスできるようにする |

**詳細仕様**
- ウィジェットタップで「買う前チェック」画面を直接起動できる。
- ウィジェット上に積読本の件数、または経過日数が長い本の情報を表示する（詳細仕様は別途デザイン確定時に決定）。
- App Groupsを用いてメインアプリとウィジェット間でデータ共有を行う。

**受け入れ基準**
- ホーム画面に追加したウィジェットをタップすると、アプリが「買う前チェック」画面を表示した状態で起動すること。
- メインアプリ側のデータ更新がウィジェット表示に反映されること。

### F-07 広告表示

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 概要 | 蔵書一覧・積読リスト画面にバナー広告を表示し、達成タイミングでインタースティシャル広告を表示する |

**詳細仕様**
- 蔵書一覧・積読リスト画面にバナー広告を常時表示する。
- 「買う前チェック」の判定結果画面には広告を表示しない。
- インタースティシャル広告は「本棚一括登録が完了した」等の達成直後のタイミングにのみ表示し、判定・購入導線の間には表示しない。

**受け入れ基準**
- 判定結果画面において広告表示が一切発生しないこと（結合テストで確認）。
- インタースティシャル広告が判定フロー（F-02）や購入導線（F-05のSafariView遷移）の途中に割り込まないこと。

### F-08 本の編集・削除

| 項目 | 内容 |
|---|---|
| 優先度 | Must |
| 概要 | 誤登録・誤判定を訂正するため、登録済みの本を編集・削除できるようにする |

**詳細仕様**
- 積読リスト・気になる本棚など、本が一覧表示される各画面から対象の本を選択し、詳細画面へ遷移できる。
- 詳細画面でタイトル・シリーズ名・巻数・所持ステータス（`OwnershipStatus`）・既読ステータス（`ReadStatus`）を手動で編集できる。
- 詳細画面から対象の本を削除できる。削除時は確認ダイアログを表示する。
- 編集・削除の結果はCoreDataに即時反映され、積読リスト・気になる本棚・シリーズ完結率（`SeriesProgress`）の再計算に反映される。

**受け入れ基準**
- 誤って登録した本を削除すると、一覧・シリーズ完結率の集計から即座に除外されること。
- タイトルや巻数を編集すると、当該シリーズの `SeriesProgress`（完結率・`missingVolumes`）が再計算されて反映されること。
- 削除操作の前に確認ダイアログが表示され、誤操作による削除を防止すること。

---

### F-09 手動追加（タイトル検索）

| 項目 | 内容 |
|---|---|
| 優先度 | Should |
| 概要 | バーコード検出・背表紙OCRのいずれでも認識できなかった場合に、タイトルを手入力・検索して登録できるようにする |

**詳細仕様**
- 「本棚に登録」「買う前チェック」の各スキャン画面から、手動検索モードに切り替えられる。
- Open Library APIへタイトルまたはISBNでの検索を行い、候補一覧から選択して登録・照合する。
- オフライン時はローカル登録済みデータのタイトルのみを対象に検索する。新規本の手動登録はタイトル・シリーズ名・巻数の直接入力で行う。

**受け入れ基準**
- スキャンに失敗した場合でも、手動検索または直接入力によって本を登録できること。
- オフライン時、ローカル登録済みデータに対する検索が機能すること。

> 本機能は元の企画書・14日ロードマップには含まれていなかった追加提案のため、優先度はShouldとする。スケジュールへの影響は第12章を参照。

## 6. データ要件

### 6.1 データモデル

```swift
// 1冊分の蔵書レコード
struct Book {
    let id: UUID
    var isbn: String?              // バーコードから取得、nilはOCR登録分
    var title: String
    var seriesName: String?
    var volumeNumber: Int?
    var coverImageURL: String?     // Open Libraryから取得しキャッシュ
    var status: OwnershipStatus    // .owned / .wishlist（気になるリスト）
    var readStatus: ReadStatus     // .unread / .reading / .finished
    var registeredAt: Date
    var lastOpenedAt: Date?
}

// シリーズ単位の所持状況（Bookから導出）
struct SeriesProgress {
    let seriesName: String
    let ownedVolumes: [Int]
    let missingVolumes: [Int]      // 既刊との差分から算出
    var completionRate: Double     // 進捗バー表示用
    var nextVolumeToBuy: Int?      // 「気になるリスト」に自動提案
}
```

### 6.2 永続化方式

- CoreDataを用い、端末内で完結させる。サーバーへの送信は行わない。
- `SeriesProgress` は永続化された `Book` レコードから都度導出する（別テーブルとして保存するか、算出プロパティとするかは実装時に決定）。

### 6.3 データ取得・キャッシュ

- 表紙画像・タイトル情報はOpen Library API取得後、端末内にキャッシュする。
- オフライン時はキャッシュ済み情報のみで表示し、判定ロジック自体（F-02）には影響しない。

## 7. 処理フロー（ロジック要件）

1. **バーコード検出**: `VNDetectBarcodesRequest`（EAN-13）でISBNを抽出。カメラをかざした瞬間に処理を開始する。
2. **ローカル照合**: CoreDataに保存済みのISBNと即時照合し、所持・未所持・巻の重複をオフラインで判定する。ネット接続は不要。
3. **メタデータ補完（任意）**: 判定後、Open Library REST API（無料・APIキー不要）にISBNを送りタイトル・表紙画像を取得しキャッシュする。オフライン時は判定機能自体は成立したまま表示のみ簡略化する。
4. **背表紙OCRフォールバック**: バーコードのない背表紙は `VNRecognizeTextRequest` でタイトル文字列を抽出し、あいまい一致で既存登録と照合する。確信度が低い場合のみ確認UIを表示する。
5. **積読リマインド**: `registeredAt` からの経過日数を計算し、閾値を超えた未読本をWidgetKit・通知でリマインドし日次利用を促す。
6. **次の購入への後押し**: 未所持判定時や完結率が閾値（例: 残り1冊）を超えた瞬間に「気になるリスト」へ自動候補表示する。タップするとISBNから楽天ブックス/Amazonの検索URLを生成しSFSafariViewControllerで開き、購入まで一気に進める。

## 9. 非機能要件

| ID | カテゴリ | 要件 |
|---|---|---|
| N-01 | 性能 | 「買う前チェック」の所持判定は、バーコード検出からオフラインで完結し、体感で即時（数百ms以内目安）に結果を表示すること |
| N-02 | オフライン動作 | 判定ロジック（バーコード検出・ローカル照合）はネットワーク接続なしで完全に動作すること。サーバーは不要 |
| N-03 | プライバシー | カメラ画像は端末内処理のみで完結し、外部送信しないこと（Open Library APIへはISBN文字列のみ送信） |
| N-04 | 対応OS | iOS（SwiftUIベース）。対応する最小バージョンについてユーザー側のこだわりはないため、実装時点のXcode最新版のデフォルト最小対応バージョンに準拠して開発者が確定してよい |
| N-05 | UI/UX | 未所持判定・シリーズ完結時にネガティブな印象を与えず、次の行動（気になるリスト追加・購入導線）へポジティブに誘導するUI表現とすること |
| N-06 | 広告体験 | 判定結果画面には広告を表示せず、判定・購入導線を広告で妨げないこと |
| N-07 | データ整合性 | 同一ISBNまたは高確度一致タイトルの本を重複登録しないこと |
| N-08 | アクセシビリティ | 標準的なiOSアクセシビリティ機能（Dynamic Type等）に配慮すること（詳細は実装時に確定） |
| N-09 | プライバシー（広告） | AdMobがIDFA等のトラッキングを行うため、iOSのApp Tracking Transparency（ATT）許諾ダイアログを適切なタイミングで表示すること。ユーザーが許諾を拒否した場合も、広告表示自体は非パーソナライズ広告として継続できること |

## 11. 制約条件・前提条件

- サーバーサイド開発は行わない（サーバー不要の設計を前提とする）。
- Open Library APIは無料・APIキー不要の範囲で利用する。将来的にAPI仕様変更・レート制限が発生した場合は代替手段を検討する。
- アフィリエイトプログラム（楽天ブックス、Amazonアソシエイト等）への登録・審査が必要である。Amazonアソシエイトは申請時に公開済みのサイト/アプリを登録する必要があるため、GitHub Pagesで公開する紹介ページ（`https://simizujob.github.io/bookReader/`、リポジトリ内 `docs/index.html`）を申請用サイトとして用いる。審査承認後180日以内に紹介実績が必要なため、開発スケジュール（第12章、約2週間）を踏まえ、開発と並行して早期に申請を行う。MVP開発期間内に審査が完了しない場合は、購入導線はアフィリエイトIDなしのリンクとして先行リリースする。
- Amazonアソシエイトのトラッキングid（ストアID）は `taros0480x84e-22` を使用する（取得済み）。楽天ブックスのアフィリエイトIDは未取得のため、取得後にF-05・第8章に追記する。
- 広告SDKはGoogle AdMob（Google Mobile Ads SDK）を採用する。IDFAトラッキングを行うためATT許諾フロー（N-09）の実装が必須となる。
- シリーズの既刊総数はOpen Library APIに依存する。同APIのデータ網羅性・正確性に起因する完結率の誤差・欠落は許容し、F-05のフォールバック仕様で吸収する。
- 単行本・文庫版など、同一作品でもISBNが異なる場合は別レコードとして扱う（データベース上での自動統合＝名寄せは行わない）。ただし「買う前チェック」（F-02）では、ISBN完全一致がない場合にF-03のあいまいタイトル一致ロジックを流用し、同タイトルの別版が登録済みである可能性を警告表示する。本格的に同一作品として統合表示する機能が必要な場合は別途要件化する。

## 13. 受け入れ基準（総合）

MVPリリース可否判定は以下をすべて満たすことを条件とする。

1. 機内モードで「買う前チェック」の所持判定が正しく動作する（N-02）。
2. 複数冊が写った本棚撮影から一括登録が行える（F-01）。
3. バーコードなし背表紙のOCRフォールバックが動作し、低確信度時は確認UIが出る（F-03）。
4. 積読リストで経過日数表示・通知リマインド・読了記録ができる（F-04）。
5. 気になる本棚でシリーズ完結率が正しく算出・表示され、書店検索への購入導線（アフィリエイトID付き）が機能する（F-05）。
6. ホーム画面ウィジェットから「買う前チェック」を直接起動できる（F-06）。
7. 判定結果画面に広告が表示されない（F-07, N-06）。
8. 同一書籍の重複登録が発生しない（N-07）。
9. 登録済みの本を編集・削除でき、削除後は一覧・シリーズ集計から即座に除外される（F-08）。
10. 既刊総数が取得できないシリーズについて、完結率を断定表示せず所定のフォールバック表示となる（F-05）。

## 14. リスク・既知の懸念

企画レビュー（Reviewer評価）で指摘された懸念点を踏まえ、以下をリスクとして管理する。

| リスク | 内容 | 対応方針 |
|---|---|---|
| 起動頻度の低さ | 書店に行く頻度は毎日ではなく、アプリを開く動機が弱い | 積読リストの経過日数バッジ・通知リマインド・読了記録機能（F-04）により、書店外でも日常的に開く理由を作る（実施済み方針） |
| 広告収益の不安定さ | 広告収益が起動頻度に依存しやすい | 気になる本棚からのアフィリエイト購入導線（F-05）を広告以外の収益源として確保する（実施済み方針） |
| OCR認識精度 | 背表紙タイトルOCRの誤認識により誤った所持判定が発生する可能性。特に日本語の縦書き背表紙は認識精度が不安定になりやすい | 確信度が低い場合は自動登録・自動判定をせず、必ずユーザー確認を挟む（F-03）。加えてF-08の編集機能で事後訂正可能にする |
| アフィリエイト審査遅延 | 審査未完了によりMVP期限内に収益導線が完成しない可能性 | 制約条件（第11章）の通り、審査未完了時はアフィリエイトIDなしで先行リリースする |
| Open Libraryのデータ網羅性不足 | 日本のコミック・シリーズの既刊総数データが取得できない、または不正確な場合がある。ユーザーの意思決定によりOpen Libraryを採用継続するが、完結率機能（F-05）の精度に直接影響する | 既刊総数が取得できない場合は完結率を断定表示せず、所持巻の最大値+1を暫定候補として示すフォールバック仕様とする（F-05）。将来的に日本語書誌データに強い代替API（例: openBD）への切り替えを検討する |
| スケジュール超過 | レビューでF-08（編集・削除）がMust要件として追加され、当初14日間の見積もりに対し負荷が増えている | Should優先度のF-09（手動検索追加）を調整弁とし、必要に応じて次バージョンへ先送りする（第12章参照） |
